# sockseek CLI playlist downloader — журнал задачі

Проєкт перейменований 11.10 22:3x на вимогу власника (був `Soulseek-Batch`). Тека задачі в
хабі лишилась `Soulseek-Batch` — її імʼя зареєстроване в `chat-map/registry.json`, і міняти
його має хаб, не я. Публічна назва й мастер-папка — `sockseek-cli-playlist-downloader`.

Машина: LITEPC, Windows 11 Pro, Version 10.0.26200.9457. Користувач: litet.
Python 3.13.14 (`py`). Дата запису: 2026-10-07. Компонент: `soulseek`.

**Це журнал задачі.** Сторінка проєкту (призначення, швидкий старт, як працює) — `README.md`,
докладний посібник англійською — `docs/README.md`, старі брифи — `docs/history/`.
**Протокол реальних тестів R1–R13 — `REAL-RUN.md`.**

**Як цим користуватись сьогодні:** `py run.py` — вибрати плейлист, подивитись, чого бракує,
підтвердити. Налаштування — `config.yaml` (теки й три значення), `sockseek.conf` (якість і очікування) та
`sockseek.local.conf` (логін, у git не йде). Той самий плейлист проганяти повторно в інший час доби: склад роздавачів онлайн
вирішує більше, ніж будь-яке налаштування. Чому саме так — розділ «Переробка воркфлоу» нижче.

## Що було не так

Словами власника: вчора ставив «180 секунд на трек», з 30 треків доїхало 14, решта «впала»,
і незрозуміло, чи то ліміт від Soulseek, чи черга (`queued`), чи в роздавача поганий інтернет.
Плюс завантажене лежало незрозуміло де.

## Корінь проблеми

| Джерело | Що там було | Примітка |
|---|---|---|
| `soulseek_batch.py`, режим за замовчуванням | **один процес sockseek на трек** | звідси три інші проблеми нижче |
| `soulseek_batch.py:build_command` | `--length-tol 1` | **жорстка** умова; дефолт sockseek — 3, у `sockseek.conf` власник поставив 6, скрипт перебивав |
| `soulseek_batch.py:parse_duration` | `int(float(part))` | обрізав дроби: `4.9` → `4`, ще майже секунда помилки до вікна ±1 с |
| `soulseek_batch.ini:8` | `track_timeout = 200` | **секунди** на трек |
| `soulseek_batch.ini:22` | `timeout = 180` | **хвилини** на спробу, лише batch-режим. Двох одиниць у назвах ключів не було — звідси «180 секунд» у памʼяті власника |
| `RUN_ME.bat:4` | `powershell -File download_all.ps1` | файла не існує, а `README.txt:12` велів клікати саме цей `.bat` |
| `README.txt:17` | «folder with the same name on your Desktop» | скрипт на Python писав у `output/<name>/` |
| `sockseek.conf` | `output-dir`, `length-tol`, `pref-format`, `pref-min-bitrate` | мертві: скрипт завжди перебивав їх з командного рядка |
| sockseek, `--help file-conditions` | «accepts common audio files with **no length metadata**» | дірка у фільтрі довжини: якщо роздавач не повідомив довжину, `--length-tol` не застосовується взагалі |
| sockseek | `--pref-min-bitrate` | лише ранжує, ніколи не відкидає — звідси файл на 84 kbps |

Чому один процес на трек ламав усе одразу в трьох місцях:

1. sockseek створює **підтеку з імені вхідного list-файла**. 30 list-файлів → 30 тек `001.list … 030.list`,
   по одному аудіофайлу в кожній.
2. Паралельність втрачалась: sockseek сам тягне `--concurrent-jobs 20`, `--concurrent-searches 2`.
3. **Лімітер пошуків живе всередині процесу.** Кожен новий процес починав зі свіжим бюджетом,
   тобто захист від 30-хвилинного бана сервера не працював.

Команда, яку тепер складає скрипт (з `--dry-run`, 07.10 09:47):

```
sockseek.exe work\<name>.list.txt --input-type list --length-tol=3
  --pref-format flac,wav,mp3 --pref-min-bitrate 320 -o output\<name>
  --name-format "{artist( - )title|filename}" --index-path output\<name>\_index.csv
  --max-stale-time 30000 --fast-search
```

Ключові зміни: `--length-tol` 1 → **3**; `--name-format` кладе файли **плоско**; `--index-path`
дає **один** `_index.csv` на плейлист; невдачі читаються з індексу, а не з коду виходу;
перші рядки кожного логу — **фактична конфігурація з джерелом кожного значення** (`cli`/`ini`/`default`).

Значення власника в ini збережені: `playlist_timeout_min = 180`, `track_timeout_s = 200`.
(Виконавець скинув їх на дефолти 60 і 300 — повернуто.)

Видалено: `RUN_ME.bat`, `README.txt`, `tracks_*.txt` (2 файли), 31 файл з `work/`.
`output/` і `logs/` не чіпали.

|---|---|---|
| Ключів у `soulseek_batch.ini` | 22 | **3 + `ffprobe_path`** |
| …з них просто пересилали значення в sockseek | 12 | 0 — **це робота `sockseek.conf`**, у якого ті самі назви й одиниці |

| `nested`, `split_artist` | завжди `false`, ніколи не мінялись | **видалено** |

| Блок конфігурації в лозі | 28 рядків на кожен запуск | **11** |

Що лишилось в ini і чому саме це: `length_tol_s` (його ж використовує перевірка ffprobe, тому
значення має бути в одному місці), `retries` (наш рівень, не sockseek), `playlist_timeout_min`
(наш таймаут процесу), `ffprobe_path`.

З 12 ключів-пересилок **10 стояли в нуль/false**, тобто вже були дефолтом sockseek і нікуди не
переїжджали. Реально переїхали два значення власника: `stale_time_s = 30` → `max-stale-time = 30000`
і `fast_search = true` → `fast-search = true` у `sockseek.conf`.

Разовий експеримент тепер не потребує ні ключа, ні коду:

```bash
cd C:/claude_tasks/Soulseek-Batch && run.cmd --only <назва> --sockseek-args="--desperate --artist-maybe-wrong"
```

Перевірено після прибирання (07.10 18:0x): **113 тестів зелені**, `--dry-run` дає код 0 і команду
без жодного зайвого ключа, логін і пароль у `sockseek.conf` незмінні (рядки звірені програмно,
у git файл не трекається).

**Доведено, що sockseek справді читає перенесені ключі**, а не тихо їх ігнорує: з навмисно битим
значенням (`max-stale-time = abc`) він падає з `Option '--max-stale-time' requires an integer
parameter, got 'abc'`, а невідомий ключ дає `Unknown argument`. Тобто і файл читається, і
друкарська помилка в ньому буде гучною, а не тихою. Перевірку робив на копії conf **без логіна
й пароля**, щоб жодного підключення не сталось.

### Три зміни 07.10 18:2x — «ок, роби 1, 3, 4» (бриф — `PLAN3.md`)

**1. Кожна невдача пояснює себе.** Після прогону скрипт шукає невдалі треки ще раз, **з усіма
умовами вимкненими** (один додатковий пошук на невдачу, вимикається `--no-explain`), і пише, що
насправді є в мережі. Плюс `reason=` тепер розшифровується текстом — бо читати його буквально
виявилось помилкою, на якій я сам спіткнувся.

**2. `Playlists/<назва>-missing.txt`** — недоїхані рядки у форматі плейлиста, з шапкою, у якій
написана команда. Наступна спроба — `run.cmd --only <назва>-missing`. Повний прогін такі файли
пропускає (`is_generated`), а прогін, після якого нічого не бракує, стирає старий файл, а не
бреше. Це і є правильний воркфлоу: доведено, що доступність треку залежить від того, хто онлайн.

**3. Код виходу розділено.** `1` = **зламався інструмент** (sockseek віддав помилку, таймаут,
не читається плейлист). Треки, яких ніхто не роздає, — це стан Soulseek, а не наша помилка, тож
прогін закінчується `0`. Підсумковий рядок один: `15 of 30 track(s) downloaded, 15 missing`.

**4. Поріг якості** `min-bitrate = 256` у `sockseek.conf` (рішення власника 13:08), свідомо
**без** `strict-conditions` — інакше відлітають усі роздавачі зі стандартним клієнтом, які
бітрейт не повідомляють. Те, що пройшло як «бітрейт невідомий», а виявилось нижчим, ffprobe
позначає в лозі `LOWQ`.

**Перекачування наявних файлів (`--skip-check-cond`) не вмикав**, хоч власник і дозволив:
не перевірено, чи sockseek не видалить старий файл, якщо краща копія не доїде. Спершу замір.

### Замір, який усе вирішив: `--strict-title` непридатний

Я збирався зробити один захід із ширшим вікном плюс жорсткий захист назви
(`--extract-artist --strict-title`). Замір на повному плейлисті (`--preview`, 30 пошуків,
нічого не качалось, тека виводу — тимчасова, щоб нічого не пропускалось):

| Умови | Скільки з 30 проходить умови |
|---|---|
| ±3 с, без захисту назви (стан на ранок) | **15** — і ці 15 лежать у теці |
| ±45 с **плюс `--extract-artist --strict-title`** | **6** |

Контроль на 5 треках, які **точно** є в мережі (їхні файли вже завантажені): з
`--extract-artist` **без** `strict-title` знайшлися всі 5, з `strict-title` — **нуль**.
Отже винен не `--extract-artist`, а сам жорсткий захист назви. Приклад, на якому це видно:
запит `London Bridge (zwilling. Edit)`, файл у мережі
`Fergie - London Bridge (zwilling. Edit) MASTER.mp3` — **містить назву дослівно** — і все одно
`StrictTitle fails`. Таку позначку має **кожен** кандидат у виводі, навіть точний збіг.

**Висновок: `strict-title` і `pref-strict-title` для наших назв не працюють і викинуті.**

### Звідки захист від підміни береться насправді

**Пошук Soulseek сам вимагає, щоб усі слова запиту були в шляху файла.** Запит
`You Got The Love (Club Calimari Remix)` несе слова `club`, `calimari`, `remix`, тому оригінал
The Source / Candi Staton у результати не потрапляє взагалі. За вечір я бачив 13 кандидатів на
5 різних треків — **ні разу** не прийшла чужа версія. ⚠ Це 13 спостережень, а не правило
протоколу, але саме вони, а не `strict-title`, і є захистом.

Тому вікно довжини можна було розширити: `length_tol_s = 45` замість 3 (дефолт sockseek, який
просто ніхто не змінював). Причина — зміряна: довжини з SoundCloud систематично **коротші** за
те, що роздають (319 с у списку, 346 с у мережі на тому самому реміксі).

Асиметричне вікно (вниз вузько, вгору широко) було б правильнішим, але **sockseek його не

### Як це тепер працює

```
py run.py
```

1. Таблиця плейлистів: назва, скільки треків, скільки **вже є**, скільки **немає**.
2. Вибір номером (`1`, `1,2`, `all`; Enter — вихід).
3. Показ, **чого саме бракує** — рядками плейлиста, з нумерацією, **до будь-якого пошуку**.
4. `y` — качає лише відсутні. `n` — не робить нічого.
5. Звіт: `OK <рядок>` на кожен доїханий, `FAILED` з причиною на кожен ні, і підсумок
   `run #NNNN: K arrived, M still missing, N of T in the folder`.

Другий раз проганяєш **той самий плейлист** — він знову порахує, чого бракує, і спитає.

| Було | Стало |
|---|---|
| `run.cmd` → прапорці руками | `run.py` (меню, статус, підтвердження); `run.cmd` — тонкий шим на нього |
| `Playlists\<назва>-missing.txt` — окремий плейлист | **видалено.** Бракуюче рахується щоразу з плейлиста й індексу |
| два заходи (A ±3, B ±45 + захист назви) | **один захід**, `length_tol_s = 45`, `min-bitrate 256` |
| наявні треки шукались, щоб sockseek їх пропустив | **не шукаються взагалі**; якщо не бракує нічого, sockseek не запускається |
| ffprobe-звіт після кожного прогону | **вимкнений**, лише з `--ffprobe-check` (власник 23:23: «поки нам не треба») |
| стеля на плейлист 180 хв | **40 хв** (реальний прогін на 30 треків — 6 хв) |

Що означає «вже є» — правило з одного рядка: **рядок індексу зі станом 1 або 3 І файл на
диску**. Лише індекс недостатньо (файл могли видалити), лише ім'я файла недостатньо — імена
приходять від роздавача (`… (Clean) 1A 142 [www.dj-promo.org].mp3`), і зв'язок із рядком
плейлиста по них не відновлюється. Якщо рядок каже «доїхало», а файла немає — лог пише
`WARN the index says this one arrived, but no file is on disk`.

### Пастка, яку зловили тести

Нова функція `config_paths` мала `app_dir: Path = APP_DIR` у підписі — і значення зафіксувалось
**на момент імпорту**. Тести ганяють увесь прогін у тимчасовій теці, підмінюючи `sb.APP_DIR`, і
одразу впали на тому, що `sockseek_exe` вказував у справжню теку проєкту. Правило: шлях за
замовчуванням читати **в момент виклику** (`app_dir = APP_DIR if app_dir is None else app_dir`),
а не в підписі функції.

### Чого sockseek НЕ вміє — питання власника про швидкість

Питання було: чи можна на ходу брати найшвидшого роздавача, а не першого. Перевірено по
`sockseek.exe --help` 11.10:

- **ранжування за швидкістю не існує.** Сортування йде за форматом, бітрейтом і назвою; швидкість
  у виводі пошуку **видно** (`(0.02MB/s)`, `(6.29MB/s)`), але на вибір вона не впливає;
- є два важелі навколо `fast-search` (обидва зараз на дефолтах): `fast-search-delay` (300 мс —
  скільки збирати кандидатів перед тим, як узяти першого) і **`fast-search-min-up-speed`**
  (мінімальна заявлена швидкість кандидата, дефолт `1`, тобто практично будь-яка);
- одиниці `fast-search-min-up-speed` у довідці **не вказані** ⚠. Непрямий замір: ті, що
  відвалювались по таймауту, мали `(0.02MB/s)` = 20 кБ/с і дефолт `1` їх не відсік, тож одиниця
  швидше за все кБ/с або Б/с, але це **не доведено**.

Тобто «найшвидший з усіх» у sockseek зробити не можна, а «не брати зовсім повільного» — можна,
одним ключем. Повний вибір дав би лише інший підхід: пошук без завантаження, власний вибір
кандидата, завантаження за `slsk://` посиланням.

**Чому мердж, а не `--user/--pass`.** Зміряно по `--help config`: sockseek читає **один** конфіг
і механізму `include` не має; профілі `[name]` всередині файла цього не вирішують. Прапорці
`--user`/`--pass` існують, але пароль у командному рядку видно в списку процесів. Тому:

```
sockseek.conf                   без секретів, публікується
sockseek.local.conf             логін + будь-який оверрайд, у .gitignore
work/sockseek.effective.conf    мердж обох, туди вказує --config
```

Мердж: ключ із локального файла **заміщає** той самий у публічному на місці, нові дописуються,
`[profile]`-секції копіюються недоторканими. Тобто локальний файл — універсальний оверрайд, а не
лише місце для логіна (`min-bitrate = 320` там працює так само).

Без логіна прогін **не стартує**: `ERROR: no Soulseek login: username, password missing in …`,
і sockseek не запускається взагалі. `--no-config` або власний `--config` через `--sockseek-args`
вимикає весь механізм — так тести ганяють sockseek у мок-режимі без логіна.

Перевірено на живому (прогін `#0032`): логін через новий файл працює (у лозі sockseek рядки про

## Пастки

- **sockseek відхиляє `--length-tol -1`** через пробіл. Треба `--length-tol=-1`. Тому `build_command`
  завжди склеює цей ключ через `=`.
- **`state=3` в `_index.csv` означає «вже є, пропущено»**, і sockseek рахує це успіхом.
  Рядки індексу **оновлюються на місці**, не додаються: після першого завантаження трек
  перемикається `1` → `3`. Код, що вважав успіхом лише `1`, звітував би **всі раніше завантажені
  треки як невдачі** на кожному повторному запуску. Знайдено трьома послідовними запусками на моках.
- **Пошук, запущений одразу після прогону, може повернути нуль кандидатів на трек, який за
  секунду до того мав їх сотні.** Зміряно двічі (`#0028`, `#0029`): трек із `reason=4` (тобто
  знайдений і спробуваний) у кроці пояснення отримав «0 candidates». Тобто крок пояснення здатен
  збрехати саме так, як я його будував не брехати. Виправлено: при `reason=4` порожній результат
  тепер читається як «пошук не відповів за 5 с», а не як «у мережі немає».
- **`--strict-title` у sockseek для наших назв зламаний.** Він відкидає навіть точні збіги
  (`StrictTitle fails` стоїть у кожного кандидата, у тому числі в імен, що містять назву
  дослівно). Без `--extract-artist` відкидає все (назва рядка = весь рядок плейлиста), з ним —
  майже все. Зміряно 23:2x: 6 із 30 проти 15. **Не використовувати ні як жорстку умову, ні як
  `pref-`.** Чому саме він так поводиться — не з'ясовано.
- **`--cond` не вміє вікна довжини.** Ключів `length`, `duration`, `dur`, `time`, `seconds` немає
  (`Unknown condition`), є лише `lengthtol` — симетричне одне число. Асиметричне вікно в один
  захід неможливе. Помилка в `--cond` вилітає **до** пошуку, тож такі перевірки безплатні.
- **sockseek ДОДАЄ рядок у `_index.csv`, а не оновлює, якщо та сама назва прийшла в іншій формі**
  (наприклад, після `--extract-artist`). Прогін `#0010` 18:52 через це звітував
  `-1 of 1 downloaded, 2 missing`. Зараз неактуально (один захід, одна форма назви), але правило
  лишається: одна команда — один `--index-path`.
- **Рядок індексу зі станом 1 або 3 ще не означає, що файл є.** Файл могли видалити руками.
  Тому «вже є» = рядок **І** файл на диску; інакше трек рахується відсутнім і шукається знову.
- **Індекс кумулятивний і ключований назвою.** Трек, прибраний з плейлиста, лишає свій провальний
  рядок назавжди — звіт читався б як «31 провал із 30 треків». Додано WARN, який це називає.
- **`--mock-files-dir` — спосіб тестувати sockseek без логіна й мережі.** Один прогін ~0,5 с.
  Жодного реального звернення до сервера Soulseek у тестах.
- `--max-stale-time` і `--search-timeout` беруть **мілісекунди**, а наші ключі — секунди.
- `open(..., "w")` на Windows конвертує в CRLF; ini і `run.cmd` писали з явним `newline`.
- Довгий heredoc у Bash-інструменті обрізався на ~108 рядку — великі файли писати файловим
  інструментом, не через `<<EOF`.
- Консоль тут cp1252: `py -c` з кирилицею падає на UnicodeEncodeError. Потрібен `errors="replace"`.
- **Колонка `length` в `_index.csv` — це довжина з плейлиста, не виміряна.** Порівняння її з
  плейлистом дає нулі в усіх рядках за побудовою і нічого не доводить. Реальну довжину дає лише
  ffprobe по самому файлу. Я на це спіткнувся: перший замір показав «усі 14 файлів ідеальні».
- **Бекслеші в шляхах, записаних через скрипт, можуть з'їстись як escape.** Константа
  `FFPROBE_FALLBACK` була записана як `C:` + FF + `fmpeg` + BS + `in` + FF + `fprobe.exe`, тобто
  `` і `` стали керуючими символами, і резервний шлях не знаходився ніколи. Приховувалось тим,
  що ffprobe є в `PATH`. Виправляти — будуючи рядок через `chr(92)`, не літералом.
- **Мок sockseek виводить довжини з назв файлів** при `--mock-files-no-read-tags`, тому мок-прогін
  потребує `--length-tol=-1` через `--sockseek-args`, інакше все падає на фільтрі довжини.
- `sed` з неекранованою `.` у шаблоні зʼїв цілий рядок markdown-таблиці. Для таких правок —
  Python `str.replace`, і перевіряти через grep.

- **`--pref-min-bitrate 320` на реальних прогонах дає різний файл на той самий трек.** У `#0002`
  `Bla Bla Bla (LTY Remix)` приїхав як **opus 65 kbps**, а 06.10 той самий трек приїхав mp3;
  `Samba De Schanero` — **opus 84 kbps**. Ключ лише ранжує, нічого не відкидає (рішення власника
  10:40 — жорсткий `--min-bitrate` не ставити). Бітрейт видно в рядку `CHECK  … br=…kbps`,
  але жодної позначки під порогом немає.
- **`Attempt: 1/1` у лозі sockseek** — спроба завантаження з кандидата одна, не 10, хоч `--help`
  обіцяє `--max-retries 10`. Коли кандидат один, альтернативи немає зовсім. Страхує лише
  наш `retries` на рівні плейлиста.

## План, якщо повернеться

1. `py run.py` — таблиця сама покаже, де що бракує. Нічого не качається без `y`.
2. Прочитати фактичну конфігурацію в перших рядках `logs/run_<NNNN>_<час>.log` — там кожне
   значення з джерелом. Не вгадувати, звідки число.
3. Рядки `FAILED` у тому ж лозі вже несуть причину словами. `reason=9` = **ніщо не пройшло
   умови** (не «немає в мережі»), `reason=4` = знайдено, але роздавач не віддав.
4. Під кожним `FAILED` стоїть результат кроку пояснення: «нічого в мережі» / «є, але відкинуто
   довжиною, візьми `--length-tol N`» / «довжина й якість ок — роздавач не віддав».
5. Якщо причина «не пройшло умови» й кандидати є — побачити їх самому:
   `py run.py --only <назва> --preview --length-tol -1`.
6. Якщо в логу `Waiting` — це лімітер пошуків (34 / 220 с), не зависання. Дочекатись.
7. Якщо «вже є» рахується неправильно — дивитись `output/<назва>/_index.csv`: «є» це рядок зі
   станом 1 або 3 **і** файл на диску.
8. Ніколи не ганяти sockseek проти реального сервера з тестів чи експериментів —
   лише `--mock-files-dir --no-config`.
